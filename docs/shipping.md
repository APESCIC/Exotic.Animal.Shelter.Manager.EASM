# How a version ships

This is the one detailed description of how work ships in EASM. `AGENTS.md`, `CONTRIBUTING.md` and the Cursor skills in `.cursor/skills/` point here instead of repeating it. Words you may not know are in the [glossary](glossary.md).

## In one paragraph

Work is grouped into versions, such as `v0.6.2`. Each issue in a version gets its own branch and pull request into the version branch. When every issue is done, the version branch goes into `main` in one merge commit, after Bambie's review. That merge commit is tagged `vX.Y.Z`, which publishes one GitHub Release, and that release is deployed once.

## The version

- A milestone's version is the `vMAJOR.MINOR.PATCH` at the start of its title, for example `v1.3.0 Beta: Public UX & compliance`. Always read it from the title, never from GitHub's milestone number.
- **The next version** is the open milestone with the lowest version above the latest tag, compared as numbers (`v0.9.0` comes before `v0.10.0`). `composer milestone:next` prints it.
- [Semantic versioning](https://semver.org/): MAJOR for breaking changes, MINOR for new features, PATCH for fixes. The milestone title sets the version; issues never change it.
- Stop and ask Bambie, without guessing, if a milestone title doesn't start with a valid version, its version isn't above the latest tag, or the version is already used on `main`. Never create, rename or delete milestones yourself.

## Names

| Item | Format | Example (`v1.3.0 Beta: Public UX & compliance`) |
| --- | --- | --- |
| Version branch | `milestone/v<MAJOR>-<MINOR>-<PATCH>-<slug>` (`composer milestone:branch`) | `milestone/v1-3-0-public-ux-compliance` |
| Issue branch | `<type>/<issue>-<slug>` (`composer milestone:branch -- --issue <n>`) | `fix/123-animal-filter` |
| Issue PR into the version branch | `[v<version>] <summary> (#<issue>)` (`composer milestone:pr-title -- <n>`) | `[v1.3.0] Keep the animal filter on reload (#123)` |
| Version PR into `main` | `v<version>: <milestone name>` | `v1.3.0: Public UX & compliance` |
| Commits | [Conventional Commits](https://www.conventionalcommits.org/) with `Refs #<issue>` | `fix: keep the animal filter on reload (Refs #123)` |
| Tag | `v<version>` | `v1.3.0` |
| GitHub Release title | `v<version> <milestone name>` (`release.yml` sets it) | `v1.3.0 Public UX & compliance` |
| Release notes | generated by `release.yml` from the merged PRs | the notes of Release `v1.3.0` |

- Issue branch types: `feature`, `fix`, `chore` or `docs`.
- Never write "Milestone 7", "#7", "[#7]", "M7" or "/milestone/7" in a branch, title, commit subject, tag or release.
- Check names with `composer milestone:check-title -- "<title>"`, `composer milestone:check-branch -- "<branch>"` and `composer milestone:check-release -- vX.Y.Z "<release title>"`. CI runs the title and branch checks on every pull request.

## Version fields

`VERSION` is the single source of the version. `composer milestone:bump -- vX.Y.Z` sets it and copies it into `config/app.php` (the `APP_VERSION` default) and `.env.example`, as listed in `scripts/MilestoneVersion/fields.json`. Never edit those by hand. The local Herd `.env` has no `APP_VERSION`, so the local preview reports the version in `VERSION`; `scripts\preview.ps1` removes one if it finds it.

## The four steps

### 1. Work

1. Run the live preview gate (the `local-setup` skill).
2. `composer milestone:next`. Create the version branch from `origin/main` if it is missing and push it (`git push -u origin HEAD`). Otherwise switch to it and merge `origin/main` into it. Merge `origin/dependencies` into it as well. Both are merge commits. Stop on any conflict.
3. Open one draft PR from the version branch into `main`, titled `v<version>: <milestone name>`, listing `Closes #<n>` for every issue including the Epic.
4. Work one issue at a time, in the planned order (the `work-on-issue` skill):
   - Create the issue branch from the version branch.
   - Post the **Work started** comment before the first commit.
   - Make small commits with `Refs #<n>` and push when useful.
   - Open a PR into the version branch with `Closes #<n>` in its description, and post **Progress update** comments at each meaningful point.
   - When CI is green, merge it into the version branch with a merge commit (`gh pr merge <pr> --merge --delete-branch`).
   - Post **Work complete**, then close the issue with `gh issue close <n> --reason completed`. GitHub only closes issues by itself on merges into `main`.
   - Check the issue shows as closed before starting the next one.
   - If that was the last open sub-issue of a parent (other than the Epic), post Work complete on the parent and close it too.
5. An issue moves to a later version only with Bambie's approval. Comment why, then move it.

The comment templates are in [reports.md](reports.md).

### 2. Merge (once per version)

When every issue in the version is closed, apart from the Epic and any "[Task] Ship the milestone" issue, which close at close-out (the `finish-version` skill). `composer milestone:status -- vX.Y.Z` still exits 1 at this point because the Epic is open; only other open issues should stop the merge.

1. Merge `origin/main` into the version branch.
2. Run `composer milestone:bump -- vX.Y.Z` as the last commit, `chore: release vX.Y.Z`, and push.
3. `gh pr ready <pr>`, then `gh pr checks <pr> --watch`. Fix any failure on the version branch.
4. Ask the **ship gate** question and wait for Bambie's answer.
5. On "merge": `gh pr merge <pr> --merge`. That is one merge commit, never a squash or rebase.

### 3. Release (once per version)

Tag the merge commit and push the tag (the `release-version` skill). `release.yml` then:

- checks that the tag matches `VERSION` and is on `main`;
- publishes the GitHub Release titled `v<version> <milestone name>`.

### 4. Deploy (once per version)

Use the `deploy-version` skill. The APES instance is a Cloudron LAMP app (since v0.6.1), deployed from GitHub Actions:

```powershell
gh workflow run deploy-cloudron.yml --ref vX.Y.Z -f tag=vX.Y.Z
gh run list --workflow deploy-cloudron.yml --limit 1 --json databaseId,url
gh run watch <id> --exit-status
```

- Run it from the tag (`--ref vX.Y.Z`). It runs in the `production` environment, which accepts only `v*` tags and holds the Cloudron settings.
- The workflow refuses a tag without a published Release or whose `VERSION` differs. It builds the release with Composer, backs up the app, uploads the release to `/app/data/releases/<id>`, runs `deploy/cloudron/activate-release.sh` (migrations once installed, then the switch of `/app/data/easm`), restarts the app and checks `/health` reports the version and the `REVISION`. If any of that fails, it switches back to the previous release.
- Migrations are never undone automatically; the pre-deploy backup covers the database.
- Evidence: the run URL, and <https://easm.intranet.apes.org.uk/health> showing the version.

### Close out

1. `composer milestone:status -- vX.Y.Z`. It lists any open issues and refuses (exit 1) while one is open. If it refuses, list those issues and stop: never close a milestone with open issues.
2. Post the **Release summary** comment on the Epic (see [reports.md](reports.md)). Close any "[Task] Ship the milestone" issue with the same summary, then the Epic, then the milestone: `gh api -X PATCH repos/APESCIC/Exotic.Animal.Shelter.Manager.EASM/milestones/<number> -f state=closed`.
3. Merge `origin/main` into `dependencies`.

## The ship gate

Before any merge into `main`, tag, release or deploy, ask Bambie exactly:

- a. Merge
- b. Release
- c. Deploy
- d. Merge, release and deploy
- e. Stop here

Run only what was chosen, in the order merge, release, deploy, and check each step. After each single step, ask again with only the steps that remain. An earlier "ship it", or an approved plan, is not an answer to this question.

## Hotfixes

Only with Bambie's written approval recorded on the hotfix issue:

1. Create a `fix/<issue>-<slug>` branch from `origin/main`.
2. Ship it as `vX.Y.(Z+1)` through the same merge, release and deploy steps.
3. Merge `main` back into the open version branch.

## Never

- Force-push, `git reset --hard` or rebase a shared branch.
- Merge into `main`, tag, release or deploy after a single issue, or without the ship-gate answer in the current chat.
- Deploy `main` or a branch; only a release tag.
- Rewrite a past tag or Release.
- Say a step happened without its command output.
